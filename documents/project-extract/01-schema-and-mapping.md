# Part A — Relational schema and mapping notes

## 1. System scope represented in the database

The schema models six application modules:

1. Shopping cart and wishlist
2. Order placement and checkout
3. Medicine catalog and inventory
4. User and role management
5. Prescription upload and verification
6. Delivery tracking and notification

The database contains 14 tables. The entities and attributes below are taken from
`database/schema.sql`; use the source DDL as the authoritative definition when preparing
the final submission.

## 2. Relation inventory

Notation: **PK** = primary key, **FK** = foreign key, **UQ** = unique constraint/index,
**CK** = check constraint. `IDENTITY` keys are generated by SQL Server.

| Relation | Main attributes and keys | Constraints / purpose |
|---|---|---|
| `users` | **PK** `id`; `full_name`, `email`, `phone`, `whatsapp`, `nic`, `date_of_birth`, `address`, `photo_key`, `password_hash`, `role`, `is_active`, `is_flagged`, `flag_reason`, `flagged_by`, `flagged_at`, `created_at`, `updated_at` | `email` UQ; self-reference `flagged_by` FK; role CK; flag-reason CK; customer-registration CK; filtered unique index on non-NULL `nic` |
| `categories` | **PK** `id`; `name`, `description`, `created_at` | `name` UQ |
| `medicines` | **PK** `id`; **FK** `category_id`; `name`, `manufacturer`, `dosage_form`, `strength`, `description`, `price`, `stock_quantity`, `reorder_level`, `requires_prescription`, `expiry_date`, `is_discontinued`, `created_at`, `updated_at` | category FK; price > 0, stock >= 0, reorder level >= 0; name index |
| `cart_items` | **PK** `id`; **FKs** `user_id`, `medicine_id`; `quantity`, `added_at`, `updated_at` | unique `(user_id, medicine_id)`; quantity > 0; deleting user cascades |
| `wishlist_items` | **PK** `id`; **FKs** `user_id`, `medicine_id`; `added_at` | unique `(user_id, medicine_id)`; deleting user cascades |
| `orders` | **PK** `id`; **FK** `user_id`; `source`, `status`, `subtotal`, `delivery_fee`, `total`, `delivery_name`, `delivery_address`, `delivery_phone`, `delivery_note`, `cancel_reason`, `created_at`, `updated_at` | source/status CKs; total = subtotal + fee; subtotal > 0; fee >= 0; user/status indexes |
| `order_items` | **PK** `id`; **FKs** `order_id`, `medicine_id`; `medicine_name`, `dosage_form`, `unit_price`, `quantity`, `dosage_instructions` | order FK cascades; quantity > 0; unit price > 0 |
| `payments` | **PK** `id`; **FK** `order_id`; `amount`, `method`, `card_last4`, `reference`, `status`, `paid_at`, `refunded_at` | one payment per order; reference UQ; status CK; order FK cascades |
| `order_status_history` | **PK** `id`; **FKs** `order_id`, nullable `changed_by`; `status`, `note`, `changed_at` | order FK cascades; records order timeline |
| `prescriptions` | **PK** `id`; **FKs** `user_id`, nullable `reviewed_by`, nullable `order_id`; `customer_note`, `file_key`, `original_file_name`, `content_type`, `file_size`, `status`, `pharmacist_note`, `reviewed_at`, `correction_count`, `uploaded_at`, `updated_at` | status/content-type CKs; paid order requires APPROVED status; file key UQ; indexes on status/time and user |
| `prescription_items` | **PK** `id`; **FKs** `prescription_id`, `medicine_id`; `quantity`, `dosage_instructions`, `unit_price` | unique `(prescription_id, medicine_id)`; quantity 1–100; price > 0; prescription FK cascades |
| `notifications` | **PK** `id`; **FK** `user_id`; `message`, `link`, `is_read`, `created_at` | user FK cascades; `(user_id, is_read)` index |
| `deliveries` | **PK** `id`; **FKs** `order_id`, nullable rider `staff_id`; `status`, `attempts`, `estimated_date`, `delivered_at`, `created_at`, `updated_at` | one delivery per order; status/attempts CKs; rider required after leaving PENDING/CANCELLED; order FK cascades |
| `delivery_updates` | **PK** `id`; **FKs** `delivery_id`, nullable `updated_by`; `status`, `note`, `created_at` | delivery FK cascades; `(delivery_id, created_at)` index |

## 3. Relationship and cardinality map

The following cardinalities are implied by the foreign keys and uniqueness constraints:

| Relationship | Cardinality | Evidence / interpretation |
|---|---|---|
| `categories` — `medicines` | One category to zero-or-many medicines; each medicine has one category | `medicines.category_id NOT NULL` FK |
| `users` — `cart_items` | One user to zero-or-many cart lines | User FK; unique user/medicine pair |
| `medicines` — `cart_items` | One medicine to zero-or-many cart lines | Medicine FK |
| `users` — `wishlist_items` | One user to zero-or-many saved lines | User FK; unique user/medicine pair |
| `users` — `orders` | One user to zero-or-many orders; each order belongs to one user | `orders.user_id NOT NULL` |
| `orders` — `order_items` | One order to one-or-many lines in normal order creation; each line belongs to one order | Order FK; application creates lines transactionally |
| `medicines` — `order_items` | One medicine can occur in many order lines | Medicine FK; line also snapshots medicine name/form/price |
| `orders` — `payments` | One order to zero-or-one payment row | `UNIQUE(payments.order_id)` |
| `orders` — `order_status_history` | One order to zero-or-many history events | History FK |
| `users` — `prescriptions` | One customer to zero-or-many prescriptions | `prescriptions.user_id NOT NULL` |
| `prescriptions` — `prescription_items` | One prescription to zero-or-many medicine lines; each line is for one prescription | Prescription FK; unique medicine per prescription |
| `medicines` — `prescription_items` | One medicine may appear on many prescription lines | Medicine FK |
| `prescriptions` — `orders` | Each prescription has zero-or-one linked paid order; an order may be referenced by a prescription | Nullable `prescriptions.order_id` FK; not unique in current DDL |
| `orders` — `deliveries` | One order to zero-or-one delivery row in the database; application creates one per paid order | `UNIQUE(deliveries.order_id)` |
| `deliveries` — `delivery_updates` | One delivery to zero-or-many tracking events | Delivery FK |
| `users` — `notifications` | One user to zero-or-many notifications | Notification FK |
| `users` — role/flag relationships | One user row may reference a flagging user and/or a delivery rider | Self-FKs `flagged_by`, `staff_id`, and event actor FKs |

The database does not enforce a minimum child count (for example, at least one
`order_items` row); that rule is enforced by the order-creation business flow. Explain
this distinction if asked about total participation.

## 4. ISA / subtype mapping

`users` is a **single-table role-discriminator design**. Customer, pharmacist, admin, and
delivery staff accounts all share one `users` relation; `role` identifies the account
type and a CHECK constraint restricts it to `CUSTOMER`, `PHARMACIST`, `ADMIN`, or
`DELIVERY_STAFF`.

This avoids duplicating shared login/contact attributes and allows foreign keys from
orders, prescription reviews, delivery assignments, notifications, and history to refer
to one account key. Customer-only attributes (`nic`, `date_of_birth`, `phone`) are
nullable in the general relation because staff need not provide all of them; a CHECK
constraint requires them when `role = 'CUSTOMER'`. This is a valid **single-table
inheritance / discriminator** mapping for overlapping shared attributes, with role-specific
rules expressed by constraints and application authorization.

There are no separate `Customer`, `Pharmacist`, `Admin`, or `DeliveryStaff` tables, and
there is no explicit ISA constraint such as total/disjoint subtype membership in the DDL.
In the EER explanation, state whether the four roles are modeled as disjoint categories
according to the system requirements; do not claim the database itself enforces
disjointness beyond its one `role` value.

## 5. Refinements and anomaly prevention

Explain these intentional design choices as refinements:

- **Cart/wishlist line uniqueness:** unique `(user_id, medicine_id)` prevents duplicate
  rows for the same item for a user.
- **Soft deletion:** `medicines.is_discontinued` keeps old order references valid rather
  than deleting a medicine and damaging transaction history.
- **Historical snapshots:** `order_items.medicine_name`, `dosage_form`, and `unit_price`
  preserve what was purchased even if the catalog later changes. Delivery details are
  copied into `orders` so later profile edits do not rewrite past orders.
- **Prescription workflow separated from product catalog:** `prescription_items` links to
  catalog medicines by FK, but stores quantity, instructions, and price at approval time.
- **Payment separated from order:** a payment has its own reference/status/timestamps,
  with at most one payment row per order; only last four card digits are stored.
- **History relations:** order and delivery changes are represented as rows, preserving
  timelines instead of overwriting the only status value.
- **Role and workflow constraints:** CHECK/UNIQUE/FK constraints reject invalid status,
  price, quantity, user-role, and ownership-link values at the database boundary.
- **Nullable optional events/fields:** an order may have no delivery rider until assigned;
  an unreviewed prescription has no reviewer; a prescription has no `order_id` until
  paid.

Avoid saying that the entire schema is in a particular normal form unless the group has
checked functional dependencies and candidate keys. Explain that the schema separates
independent entities and uses snapshots deliberately to preserve historical values.
